### Q1 (L5 iBGP split-horizon)

**问题**: Explain the iBGP split-horizon rule. Why does this rule exist, and what problem would occur without it?

**你的回答**: split-horizon is designed to deal with 'count to infinity' problem, preventing mutural dependency.

**反馈**: ✗ 混淆了。你说的"count-to-infinity + mutual dependency"是**Distance Vector的poisoned reverse**，不是iBGP split-horizon。

**标准答案**:
> iBGP split-horizon rule: A route learned via **iBGP** CANNOT be advertised to another **iBGP** peer within the same AS.
>
> Why: To prevent routing loops within the AS. iBGP peers do not change the NEXT_HOP attribute, so if R1 learns a route via iBGP from R2, and R2 advertises it to R3, R3 might think R2 is the exit point. But R2 actually depends on R1, creating a loop.
>
> Without it: AS-internal routing loops would occur, causing packets to circulate indefinitely.
>
> Solutions: full mesh iBGP (every iBGP router connects to every other), route reflector (one router relays iBGP routes), or confederation (divide AS into sub-ASes).

**区分**:
- **Poisoned reverse** (Distance Vector/RIP): neighbor tells neighbor "my distance to X is ∞" to break mutual dependency, solves count-to-infinity
- **iBGP split-horizon** (BGP): iBGP-learned route NOT advertised to other iBGP peers, prevents AS-internal loops

### Q2 (L6 三次握手)

**问题**: Why does TCP use a three-way handshake instead of two-way? What specific problem does the third message prevent?

**你的回答**: the first message intend to set up the communication. the second reply implys that the server can hear from the client. the third reply implys that the client can hear from server. After all, two machine initially can not know whether the other one can hear them.

**反馈**: △ 双向确认逻辑对了，但漏掉考试要考的关键场景。

**标准答案**:
> If only two-way handshake, an **old duplicate SYN** from a previous (already closed) connection could arrive at the server. The server would think it's a new connection request and respond with SYN+ACK. But the client would ignore this (it's not expecting a response), leaving the server with a **half-open connection** — the server thinks the connection is established, but the client doesn't.
>
> The third ACK confirms that the client is **actively participating** in this specific connection, not just responding to an old SYN.

**表述改进**:
- ✗ "the server can hear from the client" → ✓ "the server confirms receipt of the client's SYN"
- ✗ "two machine initially can not know whether the other one can hear them" → ✓ "both endpoints must synchronize sequence numbers and confirm bidirectional communication"

### Q3 (L6 3个重复ACK vs timeout)

**问题**: TCP sender receives three duplicate ACKs (e.g., ACK 100 three times). What does the sender do? How is this different from a timeout retransmission?

**你的回答**: three duplicate ACKs implys that the data package is lost during transmission, the sender would immediately cut ssthresh into the cwnd's half, set cwnd=1, and then gradually begin to grow the window size again from the lost package. 不知道和超时有什么区别

**反馈**: ✗ 混淆了。你描述的是**timeout**的行为，不是3个重复ACK的行为。

**标准答案**:
> **3个重复ACK → Fast Retransmit + Fast Recovery**:
> - 3个重复ACK说明：接收方还活着，只是某个segment丢了（后面的segment到了但乱序）
> - 动作：
>   1. **立即重传**丢失的segment（不等timeout）
>   2. ssthresh = cwnd / 2
>   3. cwnd = ssthresh + 3（**不是1**）
>   4. 进入**congestion avoidance**（线性增长）
>
> **Timeout → Slow Start**:
> - Timeout说明：segment可能丢了，或者ACK丢了，网络可能严重拥塞
> - 动作：
>   1. 重传
>   2. ssthresh = cwnd / 2
>   3. cwnd = **1**（**不是ssthresh**）
>   4. 重新**slow start**（指数增长）

**核心区别**:
| | 3 dup ACKs | Timeout |
|---|---|---|
| Network state | partial congestion (some packets arrived) | severe congestion/loss |
| Retransmit timing | immediately | after RTO timeout |
| cwnd after loss | ssthresh + 3 | 1 |
| Recovery phase | congestion avoidance (linear) | slow start (exponential) |

**类比记忆**:
- **3个重复ACK** = 快递丢了一件，但其他都到了 → fast recovery（cwnd=ssthresh+3）
- **Timeout** = 快递全丢了，或者网络大堵车 → slow start（cwnd=1）

### Q4 (L7 HTTP/2多路复用)

**问题**: HTTP/1.1 introduced pipelining, and HTTP/2 introduced multiplexing. Both reduce delay. What is the key difference, and why is HTTP/2 better?

**你的回答**: pipelining makes data package sending more fluent, without waiting the specific http request is set, while the data package still sends in strict order. Mutiplexing intend to send disorder data correctly, it gives the sender more freedom, dosen't have to wait in line.

**反馈**: △ 方向对了，但没抓住考试要的关键术语。

**标准答案**:
> In HTTP/1.1 pipelining, the client sends multiple requests over a single TCP connection without waiting for responses, but the server must respond **in order (FCFS: first-come-first-served)**. This causes **head-of-line (HOL) blocking**: a small object may wait behind a large object.
>
> In HTTP/2, objects are divided into **frames**, and frames from different objects can be **interleaved**. The server can send objects based on **client-specified priority**, not FCFS. Small objects are delivered quickly without waiting for large objects.
>
> However, HTTP/2 still runs over a single TCP connection, so **TCP-level HOL blocking** still exists (one lost segment stalls all objects). HTTP/3 (QUIC) solves this by using UDP.

**表述改进**:
- ✗ "data package" → ✓ "objects" or "responses"
- ✗ "send disorder data correctly" → ✓ "send objects out of order based on priority"
- ✗ "more freedom" → ✓ "flexibility in scheduling"
- ✗ "doesn't have to wait in line" → ✓ "avoids head-of-line blocking"

**类比记忆**:
- **HTTP/1.1 pipelining** = 餐厅点菜：你连续点5道菜，但厨师必须按顺序做（FCFS），如果第1道菜很复杂，后面都等着（HOL blocking）
- **HTTP/2 multiplexing** = 餐厅点菜（升级版）：厨师可以同时做多道菜，按优先级上菜，小菜先上

### Q5 (L7 CDN策略)

**问题**: Compare the "enter deep" and "bring home" CDN deployment strategies. What are the trade-offs?

**你的回答**: enter deep provides the most convient user 体验，while bring home are less burden and expense on maintaing CDN servers.

**反馈**: △ 方向对，但太简短，且中英混杂（"体验"）。考试必须全英文。

**标准答案**:
> **Enter deep** (e.g., Akamai): deploy CDN servers **deep into many access networks**, close to end users. Akamai has 240,000+ servers in 120+ countries. **Advantage**: lower latency (servers are closer to users). **Disadvantage**: higher maintenance cost (many small clusters to manage).
>
> **Bring home** (e.g., Limelight): deploy a **smaller number of large clusters** near access networks, not inside them. **Advantage**: lower maintenance cost (fewer locations). **Disadvantage**: higher latency (servers are farther from users).
>
> **Trade-off**: latency vs cost. Enter deep prioritizes user experience; bring home prioritizes operational efficiency.

**表述改进**:
- ✗ "most convient user 体验" → ✓ "lower latency for end users"
- ✗ "less burden and expense" → ✓ "lower maintenance cost"
- ✗ "maintaing CDN servers" → ✓ "managing CDN infrastructure"

### Q6 (跨层 端到端原则)

**问题**: Explain the end-to-end principle. Give two examples from the course that illustrate this principle.

**你的回答**: 没见过。

**反馈**: 需要讲解。

**标准答案**:
> The end-to-end principle states that application-specific functions should be implemented at the **end systems** rather than in the **intermediate nodes** (routers).
>
> **Why**: Intermediate nodes should remain simple (only forwarding); end systems have flexibility to implement different reliability mechanisms.
>
> **Examples**:
> 1. **IP is unreliable (best-effort)**: routers do not guarantee delivery; reliability is the responsibility of **TCP** at the end systems.
> 2. **IP checksum covers only the header, not the data**: data integrity is checked **end-to-end** by TCP checksum, not hop-by-hop.
> 3. **IPv6 removes checksum** from the header: error detection is left to L2 (CRC) and L4 (TCP/UDP checksum), reducing router processing burden.
> 4. **NAT violates end-to-end principle** (negative example): a middlebox (NAT router) keeps per-flow state, breaking the end-to-end model.

**记忆口诀**:
- 中间节点 = 简单、快速、无状态
- 端系统 = 复杂功能、可靠性、智能

### Q7 (L6 TCP综合题)

**问题**: Client TCP has ISN=100, Server TCP has ISN=600. MSS=536 bytes. Both rwnd=2048 bytes. Client sends 30 bytes of data. Show the TCP segments exchanged (SYN, data, ACK) with SN and AN values.

**你的回答**: [图片] 前5行正确：
| Event | SN | Ack |
|---|---|---|
| client → server | 100 | - |
| server → client | 600 | 101 |
| client → server | 101 | 601 |
| client → server | 101 | 601 |
| server → client | 601 | 131 |

**你的疑问**: 不懂MSS和rwnd有什么用，这些不是拥塞控制和计算缓存时候用的么？

**反馈**: 这道题是L6 PDF里的综合题，完整场景是：
- Client writes 30 bytes, **reads 3000 bytes**
- Server reads 30 bytes, **writes 3000 bytes**

所以Server要发3000字节给Client。这时候：

**MSS = 536** → 每个segment最多装536字节数据
- 3000 / 536 = 5.6 → 需要**6个segment**
- 5个segment各536字节 = 2680字节
- 1个segment装剩余320字节

**rwnd = 2048** → 发送方最多发2048字节的unACKed数据
- Server不能一次发完3000字节
- 先发2048字节（4个segment: 536+536+536+440）
- 等Client ACK后，再发剩余952字节

**完整segment序列**:
| Event | SN | Ack | 说明 |
|---|---|---|---|
| client → server | 100 | - | SYN |
| server → client | 600 | 101 | SYN+ACK |
| client → server | 101 | 601 | ACK |
| client → server | 101 | 601 | Data 30B |
| server → client | 601 | 131 | ACK + Data 536B (第1段) |
| server → client | 1137 | 131 | Data 536B (第2段) |
| server → client | 1673 | 131 | Data 536B (第3段) |
| server → client | 2209 | 131 | Data 440B (第4段，共2048) |
| client → server | 131 | 2649 | ACK (确认收到2048字节) |
| server → client | 2649 | 131 | Data 536B (第5段) |
| server → client | 3185 | 131 | Data 416B (第6段，共952) |

### Q8 (L7 ADSL综合题)

**问题**: A user connects to an ADSL modem at home. He types `http://www.cityu.edu.hk` in his browser. Describe the roles performed by the ADSL modem, and list the sequence of frames exchanged until the web page request is sent.

**你的回答**: modem？光猫？路由器，什么东西？解析DNS、然后转发数据包呗

**反馈**: 需要讲解。

**标准答案**:
> **ADSL Modem performs four roles**:
> 1. **DHCP server**: automatically configures the host with IP address, subnet mask, default gateway, and DNS server.
> 2. **DNS server**: resolves domain names (e.g., www.cityu.edu.hk) to IP addresses, or forwards queries to upstream DNS.
> 3. **Default gateway**: forwards packets destined for external networks (not directly reachable by the host).
> 4. **NAT**: translates the host's private IP address to a public IP address, enabling multiple devices to share one public IP.
>
> **Frame sequence** (until HTTP request):
> - Frames 1-2: ARP request/reply to discover the modem's MAC address (default gateway).
> - Frames 3-4: DNS query/reply to resolve www.cityu.edu.hk (sent to modem, which forwards to external DNS).
> - Frames 5-7: TCP three-way handshake (SYN, SYN-ACK, ACK) with the web server.
> - Frame 8: HTTP GET request.

**关键观察**:
- Frame 1-2：ARP问的是**modem的MAC**（默认网关），不是服务器的MAC
- Frame 3-4：DNS请求发给**modem**，modem再转发到外网DNS
- Frame 5-8：IP目的地址是**服务器公网IP**，但MAC目的地址是**modem的MAC**（因为要先发给modem，modem再转发）
- NAT：modem把源IP从私有IP改成公网IP，记录转换表

**类比记忆**:
- **Modem** = 你家的"网络管家"
  1. DHCP = 分配房间号（给每台设备分配IP）
  2. DNS = 通讯录（把名字翻译成电话号码/IP）
  3. Gateway = 大门（所有外出请求都从大门走）
  4. NAT = 门卫（把内部房间号转换成外部地址）

### Q9 (L6 四次挥手)

**问题**: A TCP connection is in ESTABLISHED state. The client calls `close()` to terminate the connection. List the sequence of states the client goes through until the connection is fully closed. What is the purpose of TIME_WAIT?

**你的回答**: client will send FIN signal to shutdown, and the server will comfirm this signal. But thie process only ensure that the client won't send any more message, the TIME_WAIT is designed to hold more message from server until server choose to close the communication.

**反馈**: 前半部分对，但TIME_WAIT的解释错了。

**标准答案**:
> **四次挥手完整过程**:
> 1. Client → Server: **FIN** (SN=x) → Client enters **FIN_WAIT_1**
> 2. Server → Client: **ACK** (AN=x+1) → Client enters **FIN_WAIT_2**, Server enters **CLOSE_WAIT**
> 3. Server → Client: **FIN** (SN=y) → Server enters **LAST_ACK**
> 4. Client → Server: **ACK** (AN=y+1) → Client enters **TIME_WAIT**
>
> **Client状态机**: ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → **TIME_WAIT** → CLOSED
>
> **TIME_WAIT的真正目的**（2个）:
> 1. **确保server收到最后的ACK**：如果ACK丢失，server会重发FIN，client在TIME_WAIT期间可以重新发送ACK
> 2. **让网络中的旧segment消失**：等待2×MSL（Maximum Segment Lifetime），确保这个连接的旧segment不会干扰新连接
>
> **TIME_WAIT持续时间**: 2×MSL（通常MSL=30秒，所以TIME_WAIT=60秒）

**记忆口诀**:
- FIN_WAIT_1：我发FIN了，等ACK
- FIN_WAIT_2：收到ACK了，等server的FIN
- TIME_WAIT：收到FIN了，发ACK，等2×MSL确保可靠关闭

**类比记忆**:
- **TIME_WAIT** = 挂电话后等几秒再挂断
  - 你说"再见"（FIN），对方说"再见"（FIN），你说"好的"（ACK）
  - 但对方可能没听到你的"好的"，会再说一次"再见"
  - 你等2×MSL（60秒），确保对方收到你的"好的"
  - 同时，让网络中的旧"再见"消失，防止干扰新通话

### Q10 (L6 TCP拥塞控制计算)

**问题**: TCP sender uses slow start with initial cwnd=1 MSS. MSS=500 bytes. After how many RTTs does cwnd reach 16 MSS? If a loss occurs when cwnd=16, what are the new ssthresh and cwnd values?

**你的回答**: 4RRT to reach 16MSS. If loss, ssthresh is cut to cwnd/2, and then cwnd set to 1.

**反馈**: ✓ 答案正确！

**标准答案**:
> **Slow start**: cwnd doubles every RTT
> - RTT 0: cwnd = 1 MSS
> - RTT 1: cwnd = 2 MSS
> - RTT 2: cwnd = 4 MSS
> - RTT 3: cwnd = 8 MSS
> - RTT 4: cwnd = 16 MSS
>
> **Answer**: 4 RTTs
>
> **If loss occurs when cwnd=16**:
> - ssthresh = cwnd / 2 = 16 / 2 = **8 MSS**
> - cwnd = **1 MSS** (assuming timeout loss)
> - Slow start restarts
>
> **Note**: If loss is detected by 3 duplicate ACKs (not timeout), then:
> - ssthresh = 8 MSS (same)
> - cwnd = ssthresh + 3 = **11 MSS** (not 1)
> - Enter congestion avoidance (linear increase)

**表述改进**:
- ✗ "4RTT" → ✓ "4 RTTs" (加空格)
- ✗ "ssthresh is cut to cwnd/2" → ✓ "ssthresh is set to half of cwnd (8 MSS)"
- ✗ "cwnd set to 1" → ✓ "cwnd is reset to 1 MSS, and slow start restarts"

## 主要错误模式

### 1. 概念混淆（最严重）

**iBGP split-horizon vs poisoned reverse**：
- ✗ 混淆：都是"防环"，但协议和场景不同
- ✓ 区分：
  - **Poisoned reverse**：Distance Vector (RIP)，邻居间打破循环依赖，解决count-to-infinity
  - **iBGP split-horizon**：BGP，AS内部防止路由环路，iBGP学到的路由不能通告给其他iBGP peers

**3个重复ACK vs timeout**：
- ✗ 混淆：都是丢包，但cwnd变化不同
- ✓ 区分：
  - **3个重复ACK**：网络部分拥塞（有些包到了）→ fast retransmit + fast recovery → cwnd = ssthresh + 3
  - **Timeout**：网络严重拥塞或丢失 → 重新slow start → cwnd = 1

### 2. 漏掉关键场景

**三次握手原因**：
- ✗ 只说"双向确认"
- ✓ 必须提到：**half-open connection**（旧SYN延迟到达，server误建立连接）

**TIME_WAIT目的**：
- ✗ "等server发消息"
- ✓ 两个目的：
  1. 确保server收到最后ACK
  2. 让网络中的旧segment消失

### 3. 术语不精确

| ✗ 错误表述 | ✓ 标准表述 |
|---|---|
| data package | segment (TCP) / packet (IP) / frame (L2) |
| more freedom | flexibility in scheduling |
| cut into half | set to half of |
| 体验 | experience / latency |
| 光猫 | ADSL modem |

### 4. 中英混杂

- ✗ "most convient user 体验"
- ✓ "lower latency for end users"
- ✗ "less burden and expense"
- ✓ "lower maintenance cost"
