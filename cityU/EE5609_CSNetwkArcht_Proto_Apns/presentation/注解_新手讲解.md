# 注解：从零理解 RFBus 和 IoT 架构

> 这份注解写给刚学完 TCP 的同学，假设你不懂硬件、不懂物联网、不懂协议分层。
> 我们会从最基础的问题开始，一步步解释这篇论文在做什么。

---

## 0. 你在学什么？

你刚学完 TCP，知道两台电脑怎么通过互联网可靠地传数据。但这篇论文讨论的不是"电脑之间怎么通信"，而是更底层的问题：

**"一块电路板上的芯片之间怎么通信？"**

这就像：
- TCP 解决的是"两栋楼之间怎么寄信"
- I2C 解决的是"一栋楼里两个房间之间怎么传话"

让我们从最基础的开始。

---

## 1. 芯片之间怎么说话？—— I2C 协议

### 1.1 为什么需要芯片间通信？

想象一个温度传感器节点，它有三样东西：
- **传感器芯片**：测量温度（比如 TMP1075）
- **处理器芯片**：处理数据（比如 STM32）
- **无线模块**：发送数据到远方（比如 LoRa 模块）

这三个芯片都在同一块电路板上，它们需要互相通信：
- 处理器要读传感器的数据
- 处理器要把数据发给无线模块
- 无线模块可能要配置传感器的参数

**问题**：这三个芯片怎么"说话"？

**答案**：用一根"总线"（bus）连接它们。I2C 就是其中一种总线协议。

### 1.2 I2C 是什么？

**I2C（Inter-Integrated Circuit）** 是一种**有线**通信协议，1982 年由飞利浦公司发明。

**物理结构**：
- 只需要**两根线**：
  - **SDA**（Serial Data）：数据线
  - **SCL**（Serial Clock）：时钟线
- 所有芯片都并联在这两根线上

```
        SDA 线 ───────────────────────────
              │        │        │
              │        │        │
        SCL 线 ───────────────────────────
              │        │        │
           处理器    传感器    无线模块
           (master)  (slave)   (slave)
```

### 1.3 I2C 怎么工作？

**类比**：想象一条单行道公路，上面有多个收费站。

1. **处理器（master）** 发起通信：
   - 先在 SDA 线上发一个"开始信号"（START）
   - 然后发目标芯片的地址（比如"地址 0x48 的传感器，我要读你的数据"）
   - 目标芯片回应"收到"（ACK）
   - 处理器读数据或写数据
   - 最后发"停止信号"（STOP）

2. **传感器（slave）** 被动响应：
   - 监听总线，听到自己的地址就回应
   - 把温度数据发到 SDA 线上

**关键特性**：
- **半双工**：同一时刻数据只能一个方向流动（要么 master → slave，要么 slave → master）
- **多主多从**：可以有多个 master，多个 slave
- **地址寻址**：每个 slave 有唯一地址（7 位或 10 位）
- **开漏输出**：芯片只能"拉低"电压（逻辑 0）或"释放"（高阻态），不能主动输出高电平

### 1.4 什么是"物理层"和"数据链路层"？

你学过 OSI 七层模型，I2C 工作在**最底下两层**：

```
第 7 层：应用层（HTTP、MQTT）      ← 你用的
第 6 层：表示层
第 5 层：会话层
第 4 层：传输层（TCP、UDP）        ← 你刚学的
第 3 层：网络层（IP）              ← 你刚学的
第 2 层：数据链路层（Ethernet、I2C）← I2C 在这里
第 1 层：物理层（电信号、I2C 电压） ← I2C 也在这里
```

**物理层**：定义电压、电流、引脚、时序
- I2C 的物理层：SDA 和 SCL 两根线，电压 0V（逻辑 0）或 3.3V/5V（逻辑 1）
- 时序：时钟频率 100 kbps（标准模式）或 400 kbps（快速模式）

**数据链路层**：定义帧格式、寻址、错误检测
- I2C 的数据链路层：START/STOP 条件、7 位地址、ACK/NACK、数据字节

**和 TCP 的区别**：
- TCP 工作在**传输层**（第 4 层），负责两台电脑之间的可靠传输
- I2C 工作在**物理层+数据链路层**（第 1-2 层），负责一块电路板上芯片之间的通信
- TCP 需要 IP 地址、端口号；I2C 只需要 7 位芯片地址
- TCP 可以跨互联网；I2C 只能在同一块电路板上（距离 < 1 米）

**类比**：
- TCP 是"中国邮政系统"，可以寄信到全世界
- I2C 是"房间里的传话筒"，只能在同一个房间用

## 2. I2C 的局限——为什么要无线化？

### 2.1 距离限制

I2C 设计用于**同一块电路板**上的芯片通信，典型距离：
- 标准模式（100 kbps）：< 1 米
- 快速模式（400 kbps）：< 30 厘米

**为什么距离这么短？**
- I2C 用的是**开漏输出**，需要上拉电阻把电压拉高
- 线越长，电容越大，电压上升越慢，信号越容易出错
- 超过 1 米，信号就不可靠了

### 2.2 实际场景的问题

想象你要在森林里部署 100 个温度传感器，监测火灾风险。

**方案 1：每个传感器都是独立节点**
```
传感器 1（处理器 + I2C 传感器 + LoRa）──→ 网关
传感器 2（处理器 + I2C 传感器 + LoRa）──→ 网关
...
传感器 100（处理器 + I2C 传感器 + LoRa）──→ 网关
```
- 每个节点都要有处理器（$3.3）+ LoRa 模块（$5.2）= $8.5
- 100 个节点 = $850
- 每个节点都要电池，电池只能撑几天

**方案 2：用 I2C 把所有传感器连到一个处理器**
```
传感器 1 ──┐
传感器 2 ──┤
...        ├── I2C 总线 ──→ 处理器 ──→ LoRa ──→ 网关
传感器 100 ─┘
```
- 只需要 1 个处理器 + 1 个 LoRa 模块 = $8.5
- 100 个传感器芯片 = $25
- 总成本 = $33.5（便宜多了！）
- **但是**：I2C 距离 < 1 米，100 个传感器不可能都挤在 1 米内

**问题**：怎么让相距几十米的传感器共享一个处理器？

**答案**：把 I2C 信号通过无线电波传输——这就是 **RFBus**。

## 3. RFBus 是什么？——把 I2C 无线化

### 3.1 核心思想

**RFBus = Radio Frequency Bus = 无线电总线**

**类比**：
- I2C 是"有线传话筒"，只能在房间内用
- RFBus 是"无线对讲机"，可以把传话筒的声音通过无线电传到远处

**具体做法**：
1. **Processor node**（处理器节点）：
   - 有处理器、有 LoRa/WiFi、有 RFBus 接口
   - 处理器的 I2C 信号 → RFBus 接口 → 调制到无线电波 → 发射

2. **Lite node**（简化节点）：
   - **没有处理器**、**没有 LoRa/WiFi**
   - 只有传感器 + RFBus 接口
   - 接收无线电波 → RFBus 接口 → 解调回 I2C 信号 → 传感器

```
Processor Node                    Lite Node
┌─────────────────┐              ┌─────────────────┐
│   处理器         │              │   传感器         │
│   (STM32)       │              │   (TMP1075)     │
│                 │              │                 │
│   I2C 接口      │              │   I2C 接口      │
│      │          │              │      │          │
│      ▼          │              │      ▲          │
│   RFBus 接口    │   无线电波   │   RFBus 接口    │
│   (调制+发射)   │ ──────────→ │   (接收+解调)   │
│                 │              │                 │
│   LoRa/WiFi     │              │   (无处理器)    │
│   (长距离通信)  │              │   (无 LoRa)     │
└─────────────────┘              └─────────────────┘
```

### 3.2 RFBus 解决了什么问题？

**解决的问题**：让相距 50-100 米的节点共享一个处理器。

**节省了什么？**
- Lite node 不需要处理器（省 $3.3）
- Lite node 不需要 LoRa/WiFi（省 $5.2）
- Lite node 只需要 5 个逻辑元件的 RFBus 接口（成本 $0.5）
- **每个 lite node 节省 $8.0**

**代价是什么？**
- Processor node 要额外加 RFBus 接口（成本增加 $3.6）
- Processor node 要处理 9 个 lite node 的数据（能耗增加）

**系统整体**：
- 1 个 processor node + 9 个 lite node
- 传统方案：10 个独立节点 × $8.5 = $85
- RFBus 方案：1 个 processor（$12.1）+ 9 个 lite（$5.19 × 9）= $58.8
- **节省 $26.2（31%）**

### 3.3 半双工问题——为什么需要 SPDT 开关？

**你的疑问**："为什么要'半双工射频信号控制'，传感器还会调整姿势吗？"

**解答**：半双工不是指物理姿势，而是指**通信方向**。

**I2C 是半双工的**：
- 同一时刻，数据只能一个方向流动
- 要么 master → slave（处理器写数据到传感器）
- 要么 slave → master（传感器读数据到处理器）
- 不能同时双向传输

**RFBus 的问题**：
- Lite node 没有处理器，不知道什么时候该发、什么时候该收
- 如果 lite node 一直"搬运"本地 I2C 信号到 RF，会把 processor 发的命令又发回去
- 造成**死锁**：processor 发低电平 → lite node 收到 → lite node 发低电平 → processor 收到 → 无限循环

**解决方案**：在 processor node 上加一个 **SPDT 开关**（Single-Pole Double-Throw，单刀双掷开关）

```
Processor Node
┌─────────────────────────────────────┐
│                                     │
│   处理器 ──→ I2C 接口               │
│                 │                   │
│                 ▼                   │
│            SPDT 开关                │
│           ╱        ╲                │
│          ╱          ╲               │
│         ▼            ▼              │
│   RFBus TX        RFBus RX          │
│   (发射)          (接收)            │
│         │            │              │
│         └──────┬─────┘              │
│                ▼                    │
│           无线电波                  │
│                                     │
└─────────────────────────────────────┘
```

**工作原理**：
- 当 processor 要**发命令**给 lite node 时，SPDT 开关切到 TX（发射）
- 当 processor 要**收数据**从 lite node 时，SPDT 开关切到 RX（接收）
- 切换时机由 I2C 协议的时序决定（处理器知道什么时候该发、什么时候该收）

**简单说**：SPDT 开关就像一个"对讲机的 PTT 按钮"（Push-To-Talk），按下说话，松开听。

## 4. 部署场景——为什么要用电池？

### 4.1 你的疑问

**你问**："为什么一定要装电池，然后强制去节能，而不是直接拉电线？这个东西是经常要移动的么？"

**解答**：不是经常移动，而是**无法拉电线**。

**典型应用场景**：

| 场景 | 能否拉电线 | 原因 |
|------|-----------|------|
| **森林火灾监测** | ❌ 不能 | 几千平方公里的森林，拉电线成本比设备还贵；电线容易被雷击、动物破坏 |
| **农田土壤监测** | ❌ 不能 | 农田面积大，设备分散；电线容易被农机压断；灌溉时电线泡水 |
| **桥梁结构监测** | ⚠️ 部分可以 | 桥梁本身有电，但传感器位置刁钻（桥墩内部、钢缆上、桥面下方） |
| **矿山监测** | ❌ 不能 | 矿山环境恶劣，电线容易被落石砸断；矿井深处拉电线危险 |
| **智能楼宇** | ✅ 可以 | 天花板有电灯线，可以接；但布线成本也不低 |
| **工厂设备监测** | ✅ 可以 | 设备本身有电；但设备振动会导致电线松动 |

**论文的核心场景**：野外大规模部署（森林、农田、矿区）
- 没有现成的电力基础设施
- 部署密度低（每几十米一个节点）
- 拉电线的成本远超设备本身

### 4.2 太阳能的问题

**你的疑问**："说要加太阳能板，这个东西太阳能板几乎不能覆盖能源开销，更不要说覆盖安装成本，以及太阳能发电就算很顶，发电峰值怎么存储呢？"

**你说得对**——太阳能在 IoT 中经常被过度吹捧。

**太阳能的局限**：
1. **能量密度低**：
   - 一块 5W 的太阳能板（约 30×30cm），在晴天正午能发 5W
   - 阴天只能发 0.5-1W
   - 晚上完全不发电
   
2. **储能问题**：
   - 白天发的电要存起来晚上用
   - 通常用锂电池或超级电容
   - 锂电池：能量密度高，但寿命 2-3 年，温度敏感（-20°C 到 60°C）
   - 超级电容：寿命长（10 年+），但能量密度低，存不了多少电
   - 储能系统的成本往往比太阳能板本身还高

3. **安装成本**：
   - 太阳能板要朝向南方、倾斜 30-45 度
   - 需要支架、布线、防雷
   - 在森林里，树木会遮挡阳光
   - 安装成本往往比太阳能板本身还贵

**为什么论文还提太阳能？**
- 对于 **processor node**（计算节点），太阳能可以**延长**电池寿命
- 比如：原本每月换一次电池 → 用太阳能后每年换一次
- 但你说得对：如果太阳能不能完全覆盖能耗，还是得换电池，只是频率降低
- 这是个**妥协方案**，不是根本解决

**实际情况**：
- 大多数野外 IoT 节点还是用电池
- 太阳能只用于**特定场景**（开阔地带、高纬度地区夏季）
- 更常见的方案是：**低功耗设计 + 大容量电池 + 定期维护**

### 4.3 LoRa 和 WiFi 的区别

**你的疑问**："LoRa 和 WiFi 是什么区别？"

| 特性 | LoRa | WiFi |
|------|------|------|
| **距离** | 几公里到十几公里（郊区）<br>1-2 公里（城市） | 50-100 米（室内）<br>200-300 米（室外） |
| **速率** | 0.3-50 kbps（很慢）<br>传一个温度数据（10 字节）要 2 毫秒 | 1-100 Mbps（很快）<br>传一个温度数据要 0.001 毫秒 |
| **功耗** | 低<br>发射时 50 mW<br>接收时 10 mW | 高<br>发射时 500 mW<br>接收时 200 mW |
| **成本** | 模块 $5-10 | 模块 $3-5 |
| **是否需要网关** | ✅ 需要 LoRa 网关<br>（一个网关可以覆盖几公里） | ✅ 需要 WiFi AP<br>（一个 AP 覆盖 100 米） |
| **应用场景** | 野外、农田、城市大范围<br>（森林火灾、农田监测） | 室内、办公室、家庭<br>（智能楼宇、工厂） |
| **频段** | Sub-1 GHz（433 MHz、868 MHz、915 MHz） | 2.4 GHz、5 GHz |

**为什么 LoRa 距离远但速率低？**
- LoRa 用的是**扩频技术**（Chirp Spread Spectrum）
- 把信号能量分散到很宽的频带上
- 抗干扰能力强，可以接收比噪声还弱的信号
- 但代价是速率低

**论文中的使用**：
- **室外场景**（森林、农田）：用 LoRa
  - 距离远，一个网关可以覆盖几公里
  - 速率低没关系，传感器数据量小（温度 10 字节，每分钟一次）
- **室内场景**（楼宇、工厂）：用 WiFi
  - 距离短，但速率高
  - 成本低，室内已经有 WiFi 基础设施

## 5. 整体架构——为什么不能直连中心？

### 5.1 你的疑问

**你问**："这群在想，能不能就一个计算节点，然后其他的这些传感器都能直连中心数据库，然后还要节能，这样最好？"

**解答**：你的想法有道理，但有三个问题。

### 5.2 方案对比

**方案 A：你的想法——所有传感器直连中心**
```
传感器 1 ──→ LoRa ──→ 网关 ──→ 中心数据库
传感器 2 ──→ LoRa ──→ 网关 ──→ 中心数据库
...
传感器 10000 ──→ LoRa ──→ 网关 ──→ 中心数据库
```

**问题 1：成本**
- 每个传感器都要有 LoRa 模块（$5.2）+ 处理器（$3.3）= $8.5
- 10,000 个传感器 = $85,000

**问题 2：能耗**
- 每个传感器都要用 LoRa 发数据
- LoRa 发射时功耗 50 mW
- 每分钟发一次，每次 10 毫秒
- 一天发 1440 次 = 14.4 秒
- 电池容量 2000 mAh × 3.7V = 7.4 Wh
- 电池寿命 = 7.4 Wh ÷ (50 mW × 14.4 s ÷ 3600 s) = 7.4 Wh ÷ 0.2 Wh = 37 天
- **一个月就要换电池**，10,000 个节点，维护成本巨大

**问题 3：网关负载**
- 10,000 个节点同时连接，网关要处理 10,000 个 LoRa 连接
- LoRa 网关通常只能处理 1,000-5,000 个节点
- 需要部署 2-10 个网关，成本增加

**方案 B：论文的想法——分层架构**
```
传感器 × 10,000
    ↓ I2C（有线，< 1 米）
Lite node × 9,000（无处理器，无 LoRa）
    ↓ RFBus（无线，50-100 米，低功耗）
Processor node × 1,000（有处理器，有 LoRa）
    ↓ LoRa（几公里）
网关 × 2-5
    ↓ 互联网
中心数据库
```

**优势 1：成本**
- 9,000 个 lite node：每个 $5.19 = $46,710
- 1,000 个 processor node：每个 $12.1 = $12,100
- 总成本 = $58,810（比方案 A 省 $26,190，省 31%）

**优势 2：能耗**
- Lite node 不需要 LoRa，只需要 RFBus
- RFBus 发射时功耗 0.12 mJ（传输 2 字节数据）
- LoRa 发射时功耗 50 mW × 10 ms = 0.5 mJ
- **Lite node 能耗降低 4 倍**
- 系统整体能耗降低 6 倍（论文实测）

**优势 3：网关负载**
- 只有 1,000 个 processor node 连接网关
- 一个 LoRa 网关可以处理
- 网关数量从 2-10 个减少到 1-2 个

### 5.3 为什么不能更极端——完全不要 processor node？

**你的想法**：能不能连 processor node 都不要，所有 lite node 直接连中心？

**问题**：Lite node 没有处理器，不能运行 TCP/IP 协议栈
- TCP/IP 需要处理器来运行协议栈（处理 IP 地址、TCP 连接、重传等）
- Lite node 只有 5 个逻辑元件，没有处理器
- 所以必须有 processor node 来"翻译"：I2C → RFBus → LoRa → IP → TCP

**类比**：
- Lite node 是"只会说方言的农民"
- Processor node 是"翻译官"
- 网关是"邮局"
- 中心数据库是"收件人"
- 农民不能直接给收件人写信，必须通过翻译官

## 6. RFBus、I2C 是 TCP 协议吗？

### 6.1 你的疑问

**你问**："这个 RFBus、I2C 也是 TCP 协议么？"

**解答**：**不是**，它们是完全不同层次的东西。

### 6.2 协议分层回顾

```
第 7 层：应用层（HTTP、MQTT、CoAP）      ← 你用的
第 6 层：表示层
第 5 层：会话层
第 4 层：传输层（TCP、UDP）              ← 你刚学的
第 3 层：网络层（IP）                    ← 你刚学的
第 2 层：数据链路层（Ethernet、WiFi MAC、I2C）← I2C 在这里
第 1 层：物理层（电信号、无线电波、I2C 电压） ← I2C 也在这里
```

### 6.3 对比

| 特性 | TCP | I2C | RFBus |
|------|-----|-----|-------|
| **工作层次** | 传输层（第 4 层） | 物理层+数据链路层（第 1-2 层） | 物理层+数据链路层（第 1-2 层） |
| **用途** | 两台电脑之间的可靠传输 | 一块电路板上芯片之间的通信 | 相距几十米的芯片之间的通信 |
| **距离** | 跨互联网（几千公里） | < 1 米 | 50-100 米 |
| **速率** | 几 Mbps 到几 Gbps | 100 kbps - 3.4 Mbps | 50-200 kbps |
| **寻址** | IP 地址 + 端口号 | 7 位芯片地址 | 8 位 RFBus 接口地址 + 7 位 I2C 地址 |
| **可靠性** | 重传、确认、拥塞控制 | ACK/NACK、CRC 校验 | 继承 I2C 的 ACK/NACK |
| **需要 IP 吗？** | ✅ 需要 | ❌ 不需要 | ❌ 不需要 |
| **需要路由器吗？** | ✅ 需要 | ❌ 不需要 | ❌ 不需要 |

### 6.4 它们的关系

**一个完整的 IoT 数据流**：
```
传感器（温度 25°C）
    ↓ I2C（物理层+数据链路层）
    ↓ "传感器，把温度数据给我"
    ↓ 地址：0x48
    ↓ 数据：25°C
    ↓
Lite node 的 RFBus 接口
    ↓ RFBus（物理层+数据链路层）
    ↓ 调制到 319.5 MHz 无线电波
    ↓
Processor node 的 RFBus 接口
    ↓ 解调无线电波
    ↓ 恢复 I2C 信号
    ↓
Processor node 的处理器
    ↓ 打包数据：{"node_id": 14, "temp": 25}
    ↓
Processor node 的 LoRa 模块
    ↓ LoRa（物理层+数据链路层）
    ↓ 调制到 868 MHz 无线电波
    ↓
LoRa 网关
    ↓ 解调无线电波
    ↓ 恢复 LoRa 帧
    ↓
网关的处理器
    ↓ 打包成 IP 包：src=192.168.1.1, dst=10.0.0.1
    ↓ 打包成 TCP 段：src_port=12345, dst_port=1883
    ↓
互联网
    ↓ IP（网络层）
    ↓ TCP（传输层）
    ↓
中心数据库服务器
    ↓ MQTT（应用层）
    ↓
数据库
```

**关键区别**：
- I2C/RFBus/LoRa 都是**底层协议**，负责"芯片之间怎么说话"
- TCP/IP 是**高层协议**，负责"两台电脑怎么可靠地传数据"
- 它们在不同层次，解决不同问题
- 传感器数据要经过**多次"翻译"**：I2C → RFBus → LoRa → IP → TCP → MQTT

## 7. 总结——论文的隐含假设

### 7.1 论文在解决什么问题？

**核心问题**：野外大规模 IoT 部署的成本和能耗问题。

**核心方案**：处理器共享架构 + RFBus 虚拟 I2C 总线。

**核心效果**：
- 成本降低 31%
- 能耗降低 6 倍
- 响应时间加快 2 倍

### 7.2 论文的隐含假设

**假设 1：场景是野外大规模部署**
- 无法拉电线
- 部署密度低（每几十米一个节点）
- 节点数量大（几千到几万个）

**假设 2：节点需要低功耗**
- 电池供电
- 需要长时间运行（几个月到几年）
- 维护成本高（换电池困难）

**假设 3：传感器分散在几十米范围内**
- 不能直接用有线 I2C 连接
- 需要无线连接
- 但不需要几公里的长距离（那是 LoRa 的任务）

### 7.3 如果假设不成立？

**如果可以拉电线**（比如智能楼宇）：
- 直接用有线 I2C + WiFi 可能更简单
- 不需要 RFBus

**如果节点集中**（比如工厂设备监测）：
- 所有传感器可以用有线 I2C 连到一个处理器
- 不需要 RFBus

**如果节点需要长距离通信**（比如跨城市）：
- 用 LoRaWAN 或 NB-IoT
- 不需要 RFBus

**如果节点不需要低功耗**（比如插电的设备）：
- 不需要极致节能
- 可以用更简单的方案

### 7.4 论文的价值

**价值 1：系统级思维**
- 不是"让每个节点更省电"，而是"让少数节点共享处理器"
- 从整个系统角度优化，而不是单点优化

**价值 2：协议复用**
- 把 I2C 有线总线扩展到无线
- 继承 I2C 的所有链路层服务（寻址、防碰撞、可靠传输）
- 不需要重新发明轮子

**价值 3：极简设计**
- Lite node 只需要 5 个逻辑元件
- 成本极低、功耗极低
- 适合大规模部署

### 7.5 论文的局限

**局限 1：安全性**
- 没有加密、没有认证
- RFBus 信号可以被窃听、篡改

**局限 2：可扩展性**
- 只测了 10 个节点
- 没有验证 1000+ 节点的场景

**局限 3：异构传感器**
- 只支持 I2C 传感器
- 不支持 SPI、CAN、模拟传感器

**局限 4：动态拓扑**
- 假设节点固定
- 不支持移动节点、即插即用

## 8. 常见问题解答

### Q1: RFBus 和 LoRa 是什么关系？

**A**: RFBus 和 LoRa 是**不同层次**的东西：
- **RFBus**：处理器节点和 lite node 之间的**短距离**通信（50-100 米）
- **LoRa**：处理器节点和网关之间的**长距离**通信（几公里）

**类比**：
- RFBus 是"小区内的对讲机"
- LoRa 是"跨城市的电话"

### Q2: 为什么 lite node 不需要处理器？

**A**: 因为 lite node 只需要做一件事：**把传感器数据通过 RFBus 发给 processor node**。
- 不需要运行协议栈
- 不需要做数据处理
- 不需要做路由决策
- 只需要 5 个逻辑元件的 RFBus 接口

**类比**：
- Processor node 是"经理"
- Lite node 是"工人"
- 工人只需要干活，不需要做决策

### Q3: RFBus 的通信距离为什么只有 50-100 米？

**A**: 因为 RFBus 用的是**包络检测**（envelope detection），这是一种超简单的解调方式：
- 不需要晶振、PLL 等复杂电路
- 功耗极低（μW 级别）
- 但灵敏度差，距离受限

**如果需要更远距离**：
- 用 LoRa（几公里）
- 但 LoRa 需要复杂的收发器，成本高、功耗高

**RFBus 的定位**：
- 不是替代 LoRa
- 而是补充 LoRa
- 让相距几十米的节点共享一个 LoRa 模块

### Q4: 为什么不用 WiFi 代替 LoRa？

**A**: WiFi 和 LoRa 适用场景不同：

| 场景 | WiFi | LoRa |
|------|------|------|
| 室内（智能楼宇） | ✅ 适合<br>距离短、速率高、成本低 | ❌ 不适合<br>距离太远、速率太低 |
| 室外（森林、农田） | ❌ 不适合<br>距离太短、功耗高 | ✅ 适合<br>距离远、功耗低 |

**论文中的使用**：
- 室内场景：WiFi + RFBus
- 室外场景：LoRa + RFBus

### Q5: 这篇论文和 TCP 有什么关系？

**A**: **没有直接关系**。
- TCP 是传输层协议，负责两台电脑之间的可靠传输
- RFBus 是物理层+数据链路层协议，负责芯片之间的通信
- 它们在不同层次，解决不同问题

**间接关系**：
- 传感器数据最终要通过 TCP/IP 传到中心数据库
- 但 RFBus 不关心 TCP，它只负责把数据从 lite node 传到 processor node
- Processor node 负责把数据打包成 TCP 包

**类比**：
- TCP 是"中国邮政系统"
- RFBus 是"小区内的传话筒"
- 传话筒不负责寄信，只负责把信从家门口传到邮箱
- 邮箱（processor node）负责把信交给邮局（TCP/IP）

## 10. 术语表

| 术语 | 解释 |
|------|------|
| **I2C** | Inter-Integrated Circuit，芯片间通信协议 |
| **RFBus** | Radio Frequency Bus，无线电总线，本文提出的虚拟 I2C 总线 |
| **Processor node** | 处理器节点，有处理器、有 LoRa/WiFi、有 RFBus 接口 |
| **Lite node** | 简化节点，无处理器、无 LoRa/WiFi，只有传感器 + RFBus 接口 |
| **LoRa** | Long Range，长距离低功耗无线通信技术 |
| **WiFi** | Wireless Fidelity，短距离高速无线通信技术 |
| **半双工** | Half-duplex，同一时刻数据只能一个方向流动 |
| **全双工** | Full-duplex，可以同时双向传输 |
| **开漏输出** | Open-drain output，芯片只能拉低电压或释放，不能主动输出高电平 |
| **包络检测** | Envelope detection，一种简单的 RF 解调方式 |
| **SPDT 开关** | Single-Pole Double-Throw，单刀双掷开关 |
| **CSMA/CA** | Carrier Sense Multiple Access with Collision Avoidance，载波监听多址接入/冲突避免 |
| **OSI 模型** | Open Systems Interconnection model，七层网络协议模型 |
| **TCP** | Transmission Control Protocol，传输控制协议 |
| **IP** | Internet Protocol，网际协议 |
