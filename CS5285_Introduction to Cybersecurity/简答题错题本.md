## 1. CBC vs CTR 对比类

### 题目关键词
| 看到这些词 | 想到什么 |
|-----------|---------|
| "one bit error" / "error propagation" | CBC=2块，CTR=1块 |
| "block lost" / "missing block" | CBC=丢1乱1，CTR=后续全乱 |
| "update" / "database" / "efficient" | CTR更高效（只改对应块） |
| "MAC" / "secure" | CTR不安全，CBC安全 |

### 必须回答的关键词

**Q: one bit error, which mode has less error propagation?**

✅ 必须包含：
- **CTR has less error propagation**
- CBC: **two blocks** affected (current block garbled + next block corresponding bit flipped)
- CTR: **one block** affected (only the corresponding bit)

❌ 不要写：
- "every block"（CBC不是每块都受影响）
- 公式写错（Pi = Ci xor Dk(Ci-1) ❌）

**标准答案**：
> CTR has less error propagation. In CBC mode, **two blocks** are affected: the current block is completely garbled and the next block has the corresponding bit flipped. In CTR mode, only **one block** is affected: the corresponding bit in that block is flipped.

---

**Q: block lost, which mode has less error propagation?**

✅ 必须包含：
- **CBC has less error propagation**
- CBC: **missing one block + garbled one block**, rest correct (but shifted)
- CTR: **all subsequent blocks wrong** (counter desynchronization)

**标准答案**：
> CBC has less error propagation. In CBC mode, one block is missing and one block is garbled, but subsequent blocks decrypt correctly (though shifted). In CTR mode, **all subsequent blocks are wrong** because the counter is desynchronized.

---

**Q: update records efficiently, which mode?**

✅ 必须包含：
- **CTR is more efficient**
- CBC: need to **re-encrypt all subsequent blocks**
- CTR: only need to **modify the corresponding block**

❌ 不要写：
- "parallel encryption"（虽然对，但不是update的重点）

**标准答案**：
> CTR is more efficient. In CBC mode, updating a record requires **re-encrypting all subsequent blocks** due to the chaining dependency. In CTR mode, only the **corresponding block** needs to be modified because each block is encrypted independently.

---

**Q: CTR as MAC, why not secure?**

✅ 必须包含：
- **Known-plaintext attack**
- **Recover keystream**: KS = C ⊕ P
- **Forge ciphertext**: C' = C ⊕ P ⊕ P'
- **MAC unchanged** (independent blocks)

❌ 不要写：
- "nothing can be detected"（太笼统）
- 没有给出具体公式

**标准答案**：
> CTR MAC is not secure because of **known-plaintext attack**. If the attacker knows plaintext P and ciphertext C, they can **recover the keystream**: KS = C ⊕ P. Then they can **forge a new ciphertext**: C' = C ⊕ P ⊕ P' to change the plaintext to P'. Since CTR encrypts each block **independently**, the MAC value (last ciphertext block) remains **unchanged**, so the modification is not detected.

## 2. MAC vs 数字签名类

### 题目关键词
| 看到这些词 | 想到什么 |
|-----------|---------|
| "non-repudiation" / "deny" | MAC不能，数字签名能 |
| "symmetric" / "shared key" | MAC（双方都能生成） |
| "asymmetric" / "public key" | 数字签名（只有私钥持有者能生成） |

### 必须回答的关键词

**Q: Can MAC be used for non-repudiation?**

✅ 必须包含：
- **No**
- **Symmetric key** (shared between two parties)
- **Both parties can generate** the same MAC
- **Cannot prove who sent** the message

❌ 不要写：
- "Yes"（结论错误）
- "hard to find who did bad things"（表述不清）

**标准答案**：
> **No**. MAC uses a **symmetric key shared between two parties**. Since **both parties can generate** the same MAC value, it **cannot prove who sent** the message. Therefore, MAC cannot provide non-repudiation.

---

**Q: Largest message for RSA signature? How to sign any length?**

✅ 必须包含：
- **Message must be less than n**
- **Hash the message first** (hash-then-sign)
- **Hash function** (不是hash map!)

❌ 不要写：
- "hash map"（数据结构，不是密码学）

**标准答案**：
> The largest message we can sign is **less than n** (otherwise modular arithmetic fails). In practice, we **hash the message first** using a **hash function** (e.g., SHA-256), then sign the hash value. This allows us to sign messages of **any length**.

## 3. Hash应用类

### 题目关键词
| 看到这些词 | 想到什么 |
|-----------|---------|
| "prove two files are the same" | 用hash function比较 |
| "integrity" / "tampered" | 用hash/MAC/签名验证 |
| "picture" / "document" | 计算hash值，比较是否相同 |

### 必须回答的关键词

**Q: Prove two pictures are the same (integrity)?**

✅ 必须包含：
- **Calculate hash value** (e.g., SHA-256) of both files
- **Compare** the hash values
- If **identical** → files are the same

❌ 不要写：
- "signature"（不需要证明来源）
- "from the same origin"（不准确）

**标准答案**：
> Calculate the **hash value** (e.g., SHA-256) of both pictures. If the hash values are **identical**, the two pictures are the same (with negligible collision probability).

## 4. 认证协议分析类

### 题目关键词
| 看到这些词 | 想到什么 |
|-----------|---------|
| "authentication protocol" | freshness + data origin auth |
| "nonce" / "timestamp" | freshness（防重放） |
| "signature" / "sign" | data origin auth（证明来源） |
| "unilateral" / "mutual" | 单方 vs 双向认证 |

### 必须回答的关键词

**Q: Analyze authentication protocol security**

✅ 必须包含：
- Entity authentication needs **freshness + data origin authentication**
- 分析每步消息：
  - 有nonce/timestamp? → freshness
  - 有签名? → data origin auth
- 判断认证方向：
  - A认证给B? B认证给A? 双向?

**分析模板**：
```
Message 1: A→B: RA, (RA)^A_sign
- Freshness: ❌ (RA是A生成的，不能证明实时)
- Data origin auth: ✅ (A签名了RA)
- Conclusion: A没有认证给B

Message 2: A←B: RB, (RA)^B_sign
- Freshness: ✅ (RB是B生成的)
- Data origin auth: ✅ (B签名了RA)
- Conclusion: B认证给A

Message 3: A→B: (RB)^B_enc
- Freshness: ✅ (RB是实时的)
- Data origin auth: ❌ (任何人都能用B的公钥加密)
- Conclusion: A没有认证给B

Overall: Unilateral authentication (B→A)
```

**标准答案**：
> Entity authentication requires **freshness** (using nonce/timestamp to prevent replay) and **data origin authentication** (using signature to prove sender).
> 
> - Message 1: A sends RA and signature, but RA is generated by A, so no freshness. A is not authenticated to B.
> - Message 2: B sends RB (freshness) and signs RA (data origin auth). B is authenticated to A.
> - Message 3: A encrypts RB with B's public key, but anyone can do this, so no data origin auth. A is not authenticated to B.
> 
> **Conclusion**: This is **unilateral authentication** (B authenticated to A).
