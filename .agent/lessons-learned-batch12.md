## 🔴 遇到的问题

### 1. API 路径单复数不匹配导致 404

**问题描述**：
- 前端 PetService 使用 `reminder/{id}/complete`（单数）
- 后端 ReminderController 使用 `@RequestMapping("/reminders")`（复数）
- 导致请求 `POST /api/reminder/1/complete` 返回 404 "No static resource"

**根因分析**：
- 前后端开发时未严格核对路径命名规范
- 单复数不一致是常见的命名陷阱
- 缺乏 API 路径自动化测试

**解决方案**：
- 统一使用复数形式 `reminders`（RESTful 规范）
- 修改前端 PetService.java 第 65/69 行

**经验教训**：
- ✅ **建立 API 路径对照表**：前后端开发时同步维护路径映射文档
- ✅ **使用常量定义路径**：避免硬编码字符串，使用 `const API_PATHS = { REMINDERS: "/reminders" }`
- ✅ **集成测试覆盖**：编写 API 调用测试用例，启动时自动验证路径可达

### 2. XML 布局文件残留孤立属性

**问题描述**：
- fragment_home.xml 第 50-55 行存在不属于任何标签的属性
- 导致 XML 解析错误，编译失败

**根因分析**：
- 之前使用 edit 工具修改 XML 时，old_string 和 new_string 不精确
- 替换后留下了孤立的属性片段
- 没有立即验证 XML 格式

**解决方案**：
- 删除第 50-55 行的孤立属性

**经验教训**：
- ✅ **XML 编辑后立即验证**：使用 `xmllint` 或 IDE 检查格式
- ✅ **使用结构化编辑**：避免大段替换，优先使用行号定位
- ✅ **保持 XML 格式化工具**：配置自动格式化，减少人为错误

---

### 3. Edit 工具 old_string 匹配多次

**问题描述**：
- 尝试追加内容到 error.md 时，old_string "### 状态\n待编译验证" 在文件中出现 4 次
- edit 工具报错："old_string matched 4 times"

**根因分析**：
- error.md 是迭代文档，每个批次都有相同的结尾格式
- 没有使用足够唯一的上下文

**解决方案**：
- 使用更具体的 old_string，包含表格最后一行：
  ```
  | 前端 Fragment | HomeFragment.java | Tab 渲染条件控制 |
  
  ### 状态
  待编译验证
  ```

**经验教训**：
- ✅ **追加内容使用文件末尾特征**：包含前一个章节的独特内容
- ✅ **使用行号范围读取**：先读取文件末尾，确认最后几行的唯一性
- ✅ **考虑使用 write 工具**：对于追加场景，读取全文后拼接新内容再写入

### 4. Plan Mode 提交时字符串解析错误

**问题描述**：
- 第一次调用 `exit_plan_mode` 时失败："Expected ',', got 'ident'"
- plan 字符串中包含反引号（``）和特殊字符

**根因分析**：
- plan 参数是 JSON 字符串，内部的反引号和换行符需要正确转义
- 直接在模板字符串中使用反引号会导致解析错误

**解决方案**：
- 将 plan 内容赋值给变量，避免在函数调用中直接写复杂字符串
- 使用普通字符串拼接而非模板字符串

**经验教训**：
- ✅ **复杂字符串先赋值**：避免在函数调用中直接写多行字符串
- ✅ **注意 JSON 转义**：反引号、换行符、引号需要正确处理
- ✅ **简化 plan 格式**：避免在 plan 中使用代码块，改用纯文本描述

### 5. run_code 环境不支持 require()

**问题描述**：
- 第一次尝试使用 `require('fs')` 读取文件时失败："ReferenceError: require is not defined"
- run_code 运行时使用 ESM 模块系统，不支持 CommonJS 的 require

**根因分析**：
- run_code 是 ESM 环境，需要使用 `import` 语法
- 但系统提示说"erasable syntax only"，不支持 import

**解决方案**：
- 改用 `tools.pwsh` 执行 PowerShell 命令进行文件操作
- 或使用 `tools.read`、`tools.edit`、`tools.write` 等内置工具

**经验教训**：
- ✅ **优先使用 tools.* 工具**：不要假设 Node.js API 可用
- ✅ **了解运行环境限制**：run_code 是受限的 ESM 环境
- ✅ **PowerShell 作为备选**：对于复杂文件操作，使用 pwsh 工具

## 🟢 成功的实践

### 1. 分批迭代策略

**做法**：
- 将大任务拆分为多个批次（Batch 8-12）
- 每个批次聚焦 2-4 个相关问题
- 每批次完成后更新文档

**效果**：
- 任务边界清晰，易于追踪
- 失败时影响范围可控
- 文档记录完整，便于复盘

**可复用性**：⭐⭐⭐⭐⭐

---

### 2. 前后端同步修改

**做法**：
- 修改前端 API 调用时，同步检查后端 Controller
- 修改后端接口时，同步更新前端 Service
- 使用 todo list 追踪前后端进度

**效果**：
- 避免前后端不一致导致的集成问题
- 减少调试时间

**可复用性**：⭐⭐⭐⭐⭐

---

### 3. 渐进式功能实现

**做法**：
- 先实现核心功能（P0），再实现增强功能（P1）
- 月历组件：先显示网格，再加载数据，再添加颜色
- 周报功能：先显示时间段，再添加统计数据，再添加摘要

**效果**：
- 每一步都可验证
- 失败时回滚成本低

**可复用性**：⭐⭐⭐⭐

---

### 4. 错误日志持续更新

**做法**：
- 每个批次完成后立即更新 error.md
- 记录问题描述、根因、解决方案、修改文件
- 使用统一格式，便于检索

**效果**：
- 形成知识库，避免重复踩坑
- 新成员可快速了解历史问题

**可复用性**：⭐⭐⭐⭐⭐
